0. Cold open: the pitch (0:00 to 0:50)

Screen Black. One line of text types itself: - [ ] fix-user-validation - POST /users returns 500 when name is missing. PitchHook The line drops onto a conveyor belt. It passes seven glowing stations; at each one a document pops out (spec, plan, tests, code, review), a red light turns green, and at the end a git branch slides out with two commits.

Voice-over

You paste an error from your server logs. Or you just write one line: "POST /users crashes when the name is missing."

You get a coffee, and when you come back there's a git branch waiting. In it: a written specification, a technical plan, a set of tests that failed before the fix and pass after it, the fix itself, a code review, and one clean commit.

Nobody typed any of that code. AI agents did. But here is the part that matters: at no point were those agents allowed to grade their own homework. They could not edit the tests to make them pass. They could not guess what you meant. They could not commit your secrets. And when one of them claimed "this test is wrong", a second agent, a set of mechanical checks, and a third, independent auditor all had to agree before a single test line could change.

This is a software factory. It's open source, it runs inside Claude Code, and by the end of this video you will know what a software factory is, the pattern behind this one, the safeguards that keep AI honest, how to run it on your own machine, and how you can help us turn it into a tool for every project.

Let's open the factory doors.

1. What is a software factory? (0:50 to 3:30)

Screen FactoryAnalogy A car factory in flat illustration: raw steel enters, stations weld, paint, inspect; a car rolls out. Labels appear: "stations", "conveyor", "inspection", "rejected parts bin".

Voice-over

Let's start with the word "factory". A car factory isn't one genius building a car. It's a line of stations. Each station does one job, hands its work to the next, and between the stations there are inspections. A door that doesn't fit is rejected before it reaches the paint shop, not after the car is sold.

Software has its own version of this line. It's called the SDLC: the Software Development Life Cycle. If you're new, here are the stations, in plain words:

  • Requirements: what exactly should the software do? What happens with bad input?
  • Design: which files and functions change, and in what order?
  • Tests: how will we prove it works?
  • Implementation: write the code.
  • Review: a second pair of eyes looks for bugs and security holes.
  • Release: commit it, merge it, ship it.

Screen SDLCStations The six words appear as stations on a line, each with a small icon.

Voice-over

In most teams, people do every station. A software factory automates the line. In our case the workers at each station are AI agents. And this is the first big idea of the video:

The factory is not the workers. The factory is the line, the stations, and the inspections.

An AI model that writes code is a very fast, very confident worker. Fast and confident is great on an assembly line, as long as the inspections are strict. A factory without inspections just produces broken cars faster.

Screen Split screen. Left: "AI chat: one long conversation, you check everything by eye". Right: "Software factory: separate stations, each output checked by a machine".

Voice-over

You might be using AI today like this: you open a chat, you describe a feature, the model writes code, you read it, you ask for fixes, and you hope you caught everything. That works for small things. It does not scale, and it relies on you being the only inspector.

A software factory flips that. Each AI worker gets one narrow job, a limited set of tools, and a written hand-off from the previous station. And after every station, a script, not a model, checks the result. Pass, and the work moves on. Fail, and it's rejected with a reason.

The factory runs on a real project: an open-source Node.js and PostgreSQL backend I started for a company that produces goods, sells them in its own shop and sells to dealers from the warehouse. Products, stock, invoices, GST. Ordinary business software. Which is exactly why it's a good test bed: the factory has to work on boring, real code, not on a demo.

2. The pattern behind this pipeline (3:30 to 8:30)

Screen PipelineMap The full line, left to right, with the intake dock in front of it: report -> /triage -> backlog (brief.md) -> Spec -> Plan -> Red tests -> Implement (x4) -> [Test repair] -> Review -> Ship. Each arrow carries a file name: brief.md and the index.md line, specs-1.md, plan-1.md, test-cases-1.md plus tests, source changes, review-1.md, commits.

Voice-over

Here's the whole line. It's driven by one shell script, scripts/sdlc.sh. You give it a backlog item, a short brief, and it runs these stations in order. But a factory is only as good as the raw material that comes in, so in front of the line there's an intake dock, and we'll get to it in a moment.

The pattern has four ingredients, plus the intake. Let's take them one by one.

2a. Ingredient one: a deterministic boss, AI workers

Screen BossAndWorkers A plain grey box labelled sdlc.sh (bash) holds a clipboard. Seven coloured robots line up. The box points at one robot at a time; the others stay asleep.

Voice-over

The boss of this factory is not an AI. It's about four hundred lines of bash. The script decides which station runs, starts one AI agent for that station, waits for it to finish, and then checks the result with ordinary code: does the file exist, do the tests fail, do the tests pass, did anyone touch a file they shouldn't have.

Each agent is started headless, meaning there's no chat window and no human typing: claude -p with a prompt, a list of allowed tools, and a maximum number of turns. When it's done, it's gone. The next station gets a fresh agent that knows nothing except what's written in the files.

Why does that matter? Because an AI orchestrating other AIs can be talked out of its rules. A bash if statement can't. The rules live in code, so the rules hold.

Screen capture scripts/sdlc.sh, the agent() function, highlighting claude -p "$prompt" ... --allowedTools ... --max-turns.

2b. Ingredient two: hand-offs through files

Screen FileHandOff Documents slide from robot to robot: brief, specs, plan, test cases.

Voice-over

Stations don't talk to each other. They write files. The Spec agent writes specs-1.md. The Plan agent reads that and writes plan-1.md. The Red tests agent reads both and writes a test matrix and real test files. Everything lives in Docs/backlog/<slug>/, so a human can read every hand-off, and so can the next agent. This is an old pattern called "pipes and filters": each filter does one thing and passes its output down the pipe.

2c. Ingredient three: test-driven development, red then green

Screen RedGreen A test list. All rows red. A lock icon snaps shut over the list with a git commit hash. Then the rows turn green one by one.

Voice-over

The third ingredient is test-driven development, TDD for short. If you haven't met it: you write the tests first, you watch them fail, that's "red", and only then you write the code that makes them pass, that's "green".

This pipeline takes TDD literally. After the Red tests station, the script runs the test suite. If the new tests already pass, before any code was written, the run stops with "RED GATE FAILED". A test that passes against code that doesn't exist yet proves nothing.

If they fail, as they should, the script commits them: test(<slug>): add failing tests. That commit is the lock. From that moment on, the tests are the contract. The Implement agent gets up to four attempts to make them green, and after each attempt the script compares the test folder with that locked commit. One changed line and it's "GUARD FAILED: tests were modified during implementation".

2d. Ingredient four: separation of duties

Screen MakerChecker Two columns, "Maker" and "Checker": Spec agent / developer answers; Red tests agent / red gate; Implement agent / locked tests; Test repair agent / auditor on a different model; Implement / Review agent.

Voice-over

The last ingredient is what banks call "maker-checker" and what security people call "separation of duties". The one who writes something is never the one who approves it. The agent that writes the tests doesn't write the code. The agent that writes the code can't change the tests. The agent that repairs a test is checked by an auditor that can't edit anything at all, and that runs on a different model by default, so it doesn't share the same blind spots.

So that's the pattern: a deterministic boss, AI workers with one job each, hand-offs through files, tests locked before code, and nobody grades their own homework.

2e. The intake dock: /triage builds the backlog

Screen Triage A messy pile arrives at a loading dock: a pasted stack trace, a Slack-style complaint, a line from Engineering/bugs.md. A sorting station splits it into two labelled crates, fix-user-validation (bug, P2) and add-db-health-check (feature, P2), a third scrap marked "docs only" drops into a side tray, and the crates roll onto the backlog shelf, Docs/backlog/index.md.

Voice-over

Every station we just saw starts from a backlog item. So where do backlog items come from? In a real team they come from bug reports, error logs, customer complaints, half-finished notes. Messy stuff. If you feed messy stuff straight into the line, the Spec station spends round after round asking questions.

So the factory has an intake tool: the /triage command in Claude Code. You paste whatever you have, an error message, a link to notes, a paragraph of complaints, and triage turns it into backlog items the pipeline can run with few or no question rounds. Here's what it does, in order:

  • Split. One report can hide three problems. Triage makes one item per problem and marks each as a bug, where existing behaviour is wrong, or a feature, where something new is needed.
  • Check for duplicates. It reads the backlog and the known-bugs list first. If an item already covers the report, it says which one and stops. No second copy.
  • Ground it in the code. It uses graft to find the real files, functions and endpoints. For a bug, it confirms the cause from the code, and when it's cheap and safe, it reproduces it with the tests. It says what it verified and what it didn't.
  • Decide what it can. Every question left open costs a full round at the Spec station. So triage settles what the project's own conventions already answer: the error format, the validation order, what's in and out of scope, which tests to write. It only asks you about real product decisions, up to four questions at a time, and writes your answers into the brief as decisions.
  • Write the item. A brief.md with a fixed shape: type, priority from P0 for security or data loss down to P3 for nice to have, the source, the problem, the expected behaviour, decisions, scope, tests, docs, and open questions. Plus one line in Docs/backlog/index.md, with P0 and P1 items placed above the rest, because the pipeline works top-down.

And the intake has its own safety rules. It never writes source code and never starts the pipeline. It never pastes a password or a token into a file; it names them instead. It refuses to make a backlog item for a documentation-only change, because the pipeline builds and tests code, and a docs-only item would ship docs with no feature. It tells you to edit those directly. And it never commits on its own: at the end it shows you exactly which files it would publish, to a new triage/<slug> branch, and asks. Commit and push, commit locally only, or do nothing. Anything that isn't a clear yes means do nothing.

Here's a real run. One request, "let the pipeline work with other test frameworks", went into triage and came out as three backlog items that depend on each other: a test framework registry, the pipeline gates using the configured runner, and a config screen to pick the framework. Three briefs, three lines in the backlog, one commit on a triage/ branch, which then went through a normal pull request.

Screen capture git show --stat a23b93f: three brief.md files and Docs/backlog/index.md. Then Docs/backlog/add-test-framework-registry/brief.md, highlighting Type:, Priority:, Source: and ## Decisions.

3. What is peculiar about this pipeline (8:30 to 12:00)

Screen SectionCard "What's unusual here". Then each point appears as a card.

Voice-over

Plenty of tools let an AI write code. Here's what this one does differently.

Card 1: It asks before it guesses.

Screen capture Docs/backlog/fix-user-validation-v2/decisions.md, scrolling through Q1 to Q6.

The Spec agent runs under a rule we call zero-guessing. If the brief is ambiguous, it is not allowed to invent the answer. Instead it writes questions.md: each question, why it matters, and a suggested answer. The pipeline pauses.

We tested this on purpose with a deliberately vague brief: "POST /users returns 500 when name is missing". The agent came back with six questions. What counts as a valid name? Is whitespace a name? What about extra fields like password that the old docs mentioned? Does the auth check run before validation? Each one came with a suggested answer. You type "accept", or your own answer, and the run continues. Your answers go into decisions.md and the agent is told: these are binding, never ask them again.

Card 2: Tests are locked by git, not by a promise.

We just saw this one. The lock is a commit hash. A prompt can ask an AI not to touch the tests; a git diff against that hash proves whether it did.

Card 3: "The test is wrong" is a formal claim, not an excuse.

Screen Courtroom A small courtroom: "Implement agent" files a claim, "Test repair agent" responds, "Mechanical checks" as a jury of five, "Auditor" as the judge. Gavel: VERDICT: VALID.

Sometimes a test really is wrong. It contradicts the spec, or it leaks a mock into another test. Most pipelines either let the AI edit the test, which is how cheating starts, or never let anyone fix it, which is how pipelines get stuck. Here, the Implement agent can file a claim in test-issues.md: test file, test name, and why, citing the spec. That opens Test repair, a station that only exists for this. We'll walk through its checks in the safeguards section. It's the most peculiar part of the whole factory.

Card 4: Tests must run real code.

Every prompt carries the same rule: a test must import or run the code under test. A test that reads the README and checks that a sentence is there is a defect, because it passes even when the feature is missing. Documentation is checked by the Review station, never by a test.

Card 5: Every pipeline gets its own copy of the repo.

Screen Worktrees One repo folder, two branches growing out of it into sibling folders ../production-retail-and-wholesale-sdlc/<slug>.

The wrapper, scripts/sdlc-mod.sh, runs each backlog item in its own git worktree. A worktree is a second checkout of the same repository in another folder, on its own branch. So two features can be built at the same time without stepping on each other, and your main folder stays exactly as you left it.

Card 6: Mission control lives inside Claude Code.

There's a control pane, a Claude Code plugin called sdlc-monitor. You start runs, watch stages, answer questions, allow or deny actions, and stop or discard runs, without leaving your editor session. We'll demo it in a minute.

Card 7: Bring your own model.

Each station has its own model and effort level. By default, the thinking-heavy stations, Spec, Plan, Test audit and Review, use Opus, and the doing stations use Sonnet. You can override any station, and you can point a station at another provider's Anthropic-compatible endpoint, such as a LiteLLM or OpenRouter gateway.

Card 8: The factory was built by the factory.

Screen capture Docs/backlog/index.md, highlighting [x] add-model-registry, [x] add-config-pane, [x] add-permission-prompts, [x] retry-unclaimed-failing-test.

And maybe the most fun detail: many of the pipeline's own features went through the pipeline. The model registry, the config pane, the permission prompts, the flaky-test retry: each started as a backlog line, got a spec, locked tests, and an implementation. There are even three deprecated versions of the runner still in the repo, a nice record of how the design grew up.

4. The safeguards, and why each one exists (12:00 to 16:30)

Screen SafeguardStack A tall stack of shields. Each shield, as it is named, slides in with a short "threat" label on the left and "mechanism" label on the right.

Voice-over

Now the heart of it. A safeguard is only worth having if you can say what it protects against. So for each one: the threat, and the mechanism.

1. The red gate.

Threat: tests that pass before the code exists, so they test nothing. Mechanism: after Red tests, the suite must fail, or the run stops.

2. The test lock.

Threat: an agent under pressure "fixes" the failing test instead of the code. Mechanism: the tests are committed, and after every Implement attempt and after Review, any difference in server/__tests__ from that commit stops the run.

3. The stage guard plugin.

Threat: an agent writing files outside its job, during the stage. The git check catches it afterwards; we'd rather stop it in the act. Mechanism: the sdlc-guard plugin is loaded into every agent. It reads the current stage from status.json and refuses writes the stage doesn't allow. Spec and Plan may only write their own docs folder. Red tests may write tests and docs, never source. Implement and Review may never write tests, not even through a sneaky sed -i or mv in the shell. It also refuses a plan written before the spec exists. And if the guard itself crashes, it refuses the call. A crashed check must not become an open door.

Screen capture .claude/plugins/sdlc-guard/hooks/register.ts, the refuse() switch and the FAILED constant.

4. The Test repair chain.

Screen RepairChain Seven links of a chain light up one by one. If any link breaks, the chain snaps and a "tests restored" stamp appears.

Threat: a legitimate "this test is wrong" claim becomes a loophole. So Test repair is a chain, and every link has to hold:

  1. Flaky filter. Failing tests that weren't claimed are re-run once. If one passes, it's flaky: recorded as a warning in flaky-tests.md, not blamed on anyone.
  2. Pre-check. Every still-failing test must be claimed, and at most three tests can be claimed. You can't claim your way out of the whole suite.
  3. Hands off the source. The repair agent may edit only the claimed test files. A hash of the source is taken before and after; if it changed, rejected.
  4. Diff check. Only claimed files changed. No fewer expect() calls than before. No new weak matchers like toBeTruthy or expect.anything. No new skip, only or todo.
  5. Name check. Every test that existed when the tests were locked still exists. No deleting, no renaming.
  6. Red check. The repaired tests are run against the original, unimplemented code. They must still fail there. A repaired test that passes on empty code was weakened.
  7. Independent audit. A read-only auditor, on a different model by default, reads the spec, the claim and the diff, and must end with exactly VERDICT: VALID. Its instructions end with: "If in any doubt, INVALID."

Only then is the repair committed and the tests locked again. If any link breaks, the tests are restored to the locked commit. And the repair agent can also say "no repair needed: the code is wrong", which sends the work back.

5. Real integration tests.

Threat: unit tests that mock the database pass while the real SQL is broken. Mechanism: after the unit tests, the integration suite runs against real PostgreSQL. It uses your local database if it answers, or starts a throwaway Docker container, and it creates and drops its own prw_test_* databases so it never touches your data. A remote database is ignored unless you opt in.

6. Scoped tools, bounded turns, and asking permission.

Threat: an agent running commands nobody approved. Mechanism: each agent gets a short list of allowed tools: read, write, edit, search, npm test, lint, a few read-only git commands. Turns are capped. If an agent tries something outside the list, it's refused, the run pauses, and the pane shows the refused action with three buttons: Allow this run, Allow always, Deny. Then the stage restarts. Headless agents can't ask you questions, so the pipeline asks for them.

7. Keys stay secret.

Threat: an API key leaking into a log, a command line, or the wrong company's server. Mechanism: the model registry stores the name of the environment variable, never the key. The key is exported only inside the subshell that starts the agent. Your Anthropic key is blanked for that call so it's never sent to a third-party endpoint. And endpoints must be https, or plain http only to localhost.

8. Ship commits only what the factory built.

Threat: the pipeline commits your unrelated work in progress, or your .env file. Mechanism: at the start, the script takes a snapshot of every file you'd already changed. At the end, Ship commits only what changed since then. Secrets like .env and *.pem, editor and agent config, generated files and anything over 1 MiB are skipped and listed in ship-skipped.md. New keys added to .env are copied to .env.example with the value change-me, never the real value.

9. Nothing is lost by accident, and nothing merges by accident.

Threat: a "discard" that throws away a day of work, or a bot that merges to main. Mechanism: before discard or restart deletes a branch, the branch tip is saved, and the command to bring it back is printed. And the house rules for the orchestrating Claude session say: never merge a pull request without asking the human first, with an explicit Merge or Do not merge choice. A green CI run is not a yes.

Screen SafeguardStack collapses into one sentence.

Voice-over

If you remember one thing from this section: agents propose, gates dispose. The AI does the creative work. Plain code decides whether it's accepted.

5. How to use it today (16:30 to 21:30)

Screen WhereItLives A warehouse building labelled production-retail-and-wholesale (stock, own shop, dealers and retailers, accounting). Inside it, a small glowing room labelled "software factory". A dotted outline next to the building shows where the factory will move out on its own: "standalone library", then "app for developers".

Voice-over

Before we run it, a word on where this factory lives, because I want to be upfront about it.

It's built into an open-source project I started a while back and never finished: production-retail-and-wholesale. It's a proof of concept for a company that makes its own products, sells them in its own shop, and sells to dealers and retailers straight from the warehouse. Warehouse and stock management, sales, and accounting.

I built the factory inside that project to finish it, so today it's wired to that one codebase. It isn't reusable yet. You can't drop it into your own repo and run it.

That's changing. I'm pulling it out into a standalone open-source library, and eventually an app, to support developers on any project. I've only just started on that, and I'll keep posting steady progress on this channel.

So what you'll see now is how to try it today, inside this project. It's the best way to see every station working for real, and the best starting point if you want to help build the standalone version.

Screen Checklist Prerequisites ticking in: Node.js, git, Claude Code, graft, PostgreSQL or Docker.

Voice-over

Let's run it. You need Node.js, git, Claude Code, and Docker or a local PostgreSQL for the integration tests. You also need graft, a code-graph tool the Plan station uses to find which files a change touches.

Screen capture Terminal:

git clone https://github.com/imaimai86/production-retail-and-wholesale
cd production-retail-and-wholesale
npm install -g @nanonets/graft
graft build
./install.sh

Clone the repo, install graft, build the graph, and run install.sh to install dependencies.

Step 1: describe the work.

Screen capture Claude Code, typing /triage POST /users returns 500 when the name is missing.

Every job starts as a backlog item: a line in Docs/backlog/index.md and a short brief.md. You can write them by hand, but the easy way is the intake dock we saw earlier: paste the bug report into /triage. It splits it, checks for duplicates, finds the real files with graft, asks you only what the code can't answer, and writes the brief and the backlog line. It ends with a table of the items it made and the command to run each one, and offers to publish them to a triage/<slug> branch once you say yes. To see what's waiting, run /backlog-list pending.

Step 2: start a run.

Screen capture

bash scripts/sdlc-mod.sh run fix-user-validation
bash scripts/sdlc-mod.sh watch fix-user-validation

Start it with sdlc-mod.sh run and the slug. That creates the worktree and branch sdlc/<slug> and starts the pipeline in the background. Up to two run at once; a third waits. watch gives you a live view: the status line, the current stage and model, the uncommitted files, and the last lines of output.

Step 3: or use the control pane.

Screen capture Claude Code started with the plugin; the SDLC button above the prompt; the overview with pending items and checkboxes; Run selected; then a pipeline view with stage chips, progress bar, current agent, elapsed time, attempt 2/4, test progress and "Files changed per stage".

claude --plugin-dir .claude/plugins/sdlc-monitor

Most people will prefer the pane. Start Claude Code with the sdlc-monitor plugin and press SDLC, or type /sdlc-monitor. The overview lists pending backlog items with checkboxes and every pipeline with its state: running, paused, done, failed or interrupted, and how many files it has changed. Tick two items, press Run selected. Open a pipeline and you see each stage as a chip, the model and effort under each stage, the agent that's running right now with its elapsed time and attempt number, test progress, the documents produced so far, and which files each stage changed.

Step 4: answer the questions.

Screen capture A toast "fix-user-validation is waiting for answers"; the Answer button; each question with Use suggested; then Submit answers and resume.

When the Spec agent has questions, you get a toast and an Answer button. Each question shows its suggested answer. Press Use suggested or type your own, then Submit answers and resume. If you work from the terminal, you fill the **Answer:** lines in questions.md and run the same command again.

Step 5: steer, stop, resume.

Something going the wrong way? Stop, press twice to confirm. A stopped or failed pipeline shows a text box per stage. Type an instruction for that stage, for example "keep the existing error format", press Resume at Implement, and that text is handed to the agent as binding input. From the terminal it's FROM=implement before the command. And Discard throws the attempt away and lets you start fresh, with the old branch recoverable.

Step 6: configure models.

Screen capture The CONFIG pane: a provider row, Test on a model, a toast "ok".

The CONFIG button opens the model registry: add a provider, its endpoint, the name of the variable that holds its key, and its models. Press Test to send one request and see if it answers. Then pick models per stage, for example MODEL_IMPLEMENT=opus EFFORT_IMPLEMENT=high.

Step 7: review the result.

Screen capture git log --oneline on sdlc/fix-user-validation-v2: test(...): add failing tests and spec/plan docs, feat(...), and the backlog tick.

When it's done you have a branch with the locked tests commit, the feature commit, and the backlog item ticked. Read the spec, the plan and the review in the docs folder, look at the diff, and open a pull request. The factory builds; a human still decides what ships.

6. Where it's going: the roadmap and ai-sdlc-helper (21:30 to 23:15)

Screen Roadmap A road with two lanes: "Next in this repo" and "ai-sdlc-helper".

Voice-over

As I said, today this factory is wired into one project: Jest tests in server/__tests__, npm test, PostgreSQL. The next big step is to lift it out so any project can use it: first as a standalone open-source library, and eventually as an app for developers. I call it the ai-sdlc-helper. The working name in the plan is sdlc-helper, and the final name is still open.

Screen Two boxes: "npm package: the engine (CLI, pipeline, test adapters, registries, prompts)" and "Claude Code plugin: the interface (slash commands, control pane, guard hooks, working rules)".

It ships as two pieces from one repo. An npm package is the engine: the command-line tool, the pipeline, the model registry and the default prompts. It works without any UI, so it runs in a terminal or in CI too. And a Claude Code plugin is the interface: the slash commands, the control pane, the guard, and the working rules that today live in this repo's CLAUDE.md.

Each project gets a small sdlc.config.json: where the backlog lives, which test suites exist, which test runner, the integration command, branch names. And sdlc-helper add will look at your project and propose that config for you.

The key piece is test runner adapters. Every runner gets a small adapter that turns its output into one common result shape. The first release targets Node and TypeScript: Jest, Vitest, Mocha and node:test, plus a generic JUnit XML adapter so other languages can already plug in. Python, Go, Rust, Java, .NET, Ruby and PHP come after launch.

The engine moves from bash to TypeScript, so it's unit-testable and runs on Windows without WSL. And end-to-end checks will run the whole pipeline on sample projects in CI, with the AI replaced by a recorded stub so CI needs no API key.
