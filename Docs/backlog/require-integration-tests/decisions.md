
## Round 1 (2026-10-07)

### Q1: Diff gate baseline when the run resumes at Review after a Test repair
The diff gate runs `git diff --name-only <orig_red_sha>~1 <orig_red_sha> -- server/__tests__/integration/`. On a resume (`FROM=implement`, `FROM=test-repair`, `FROM=review`), `scripts/sdlc.sh` sets `ORIG_RED_SHA="$RED_SHA"` (line 194). On `FROM=review` after a Test repair, `RED_SHA` is the "repair invalid tests" commit, so `orig_red_sha~1..orig_red_sha` covers only that repair commit. That commit may not touch `integration/`, and the gate would then reject a run whose real red commit did contain integration tests. The brief says the orig sha keeps the gate correct "after a Test repair commit", but it does not say how the orig sha is found on a resume. Which commit should the integration-test check use?
**Suggested:** On every resume, use the original red-tests commit (`git log --grep="^test($SLUG): add failing tests"`) as `<orig_red_sha>` for the integration-test check only. The existing `RED_SHA` and `ORIG_RED_SHA` handling stays unchanged for the other guards.
**Answer:** accept

## Round 2 (2026-10-08)

### Q1: Do untracked files count as source changes and as integration tests?
The diff gate uses `git diff -U0 -w --ignore-blank-lines` against `<red_sha>`. That command ignores untracked files. A new migration such as `server/migrations/003_add_refunds.sql` created by the Implement agent is untracked until Ship, so the gate would never see the most common DB change. The same applies to a `plan` check that looks for "new or modified" files under `<test-dir>/integration/` before the red commit exists: a brand-new integration test file is untracked. Should untracked files be included in both checks?
**Suggested:** Yes. For the `plan` check, "new or modified" means differing from `HEAD` or untracked (and not ignored) under `<test-dir>/integration/`. For the diff gate, untracked files under the source paths count as source changes, with every line treated as added, so a comment-only new file is ignored like any other comment-only change.
**Answer:** Tracked changes only: untracked files do NOT count, in either the diff gate or the `plan` check; only changes git reports against the comparison commit count. (The user chose this knowing a new migration or a brand-new integration test file created by an agent stays untracked until it is committed and so is not seen by the checks before that. Spec: say clearly where in the flow the checks run so that files are tracked when they are checked, or state the limitation.)

### Q2: Where does the Plan stage check for the `## DB and API changes` section?
The brief says a missing section "fails the Plan stage" with `Plan has no '## DB and API changes' section`, and also defines `plan <plan-1.md> <test-dir>` in `scripts/sdlc-integration-gate.cjs` with a section check implied. It does not say whether `scripts/sdlc.sh` checks the section right after the Plan agent writes `plan-1.md`, or only the gate script checks it (at the Red tests stage, after the agent has already run). It also does not say what a malformed bullet (one not matching the listed forms) or an empty section does. This decides whether a bad plan fails fast at Plan and whether a resume with `FROM=red-tests` is checked too.
**Suggested:** `scripts/sdlc.sh` runs the gate's `plan` check in structure-only mode immediately after the Plan agent finishes, and the full `plan` check (structure plus tokens in the integration files) before the Red tests unit red gate, so `FROM=red-tests` resumes are covered. Structure-only means: the section must exist, and every bullet must match one of the six listed forms or the single `- none` bullet. A missing section, an empty section, an unrecognised bullet, or `- none` mixed with other bullets is a `REJECT:` line and exit 1. A rejection stops the pipeline with exit 1.
**Answer:** Check only at Red tests: no early check right after the Plan agent. The gate script checks the `## DB and API changes` section at the Red tests stage. (This replaces the suggested structure-only check at Plan; a bad plan costs one Red tests agent run before it is rejected.)

## Round 3 (2026-10-08)

### Q1: Must the unit red gate still fail the run when only integration tests are new?
The red gate in `scripts/sdlc.sh` currently stops with `RED GATE FAILED: new tests pass before implementation` whenever `npm test` passes (`tests_pass`). `jest` ignores `__tests__/integration/`, so a change that is purely a DB or API addition (for example a new migration plus a new endpoint covered only by integration tests, with no new unit test) can leave `npm test` green at Red tests. The brief adds the integration red check after the `plan` check passes, but does not say how it combines with the unit red gate when the plan section is not `- none`. This decides whether such a run can ever reach the integration red check at all, or is rejected by the unit gate first.
**Suggested:** When the section is not `- none`, the red gate passes if EITHER `npm test` fails OR the integration red check (`bash scripts/sdlc-integration.sh`) exits 1; it fails with `RED GATE FAILED` only if both pass (the unit `tests_pass` message is kept when the section is `- none` and unit tests pass). Order: `plan` check, then unit run, then the integration red check always runs when the section is not `- none` (exit 0 still prints its own `RED GATE FAILED: new integration tests pass before implementation` message, because the integration tests must fail regardless of the unit result; exit 3 still stops the run).
**Answer:** accept

## Round 4 (2026-10-08)

### Q1: What exit code does `sdlc-integration.sh` use when the Docker database container never becomes ready?
The brief changes `scripts/sdlc-integration.sh` to exit 3 for "the two infrastructure errors only": no `test:integration` script (line 14) and no `DATABASE_URL` or docker (line 77). The script has a third infrastructure error: `ERROR: database container not ready after 60 attempts` (around line 72), which currently exits 1. The new Red gate treats exit 1 as the expected red result ("tests failing"). If this error keeps exit 1, a Docker container that fails to start would be read as a passing red check, and a run could reach Implement and Ship without any integration test ever having failed. The brief's "two ... only" wording does not say whether this third case is deliberately left at 1.
**Suggested:** Exit 3 for the container-not-ready error too, so exit 3 means "the integration suite could not run" in all three cases. The Red gate then stops with `ERROR: no database for the integration red check (set DATABASE_URL or start Docker)`. Add a test in `sdlc-integration.test.js` for it if one can be done without a real container; otherwise list it as a review item.
**Answer:** accept
