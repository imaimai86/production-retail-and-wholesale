3. **Implement the validation, `server/index.js` `POST /users` handler**
   - At the top of the `try` (before `Users.create`), read `const { name } = req.body || {};`. `express.json()` leaves `req.body` as `{}` for an empty body, but the guard keeps a non-object body from throwing.
   - Order matters, because of the rules in the spec:
     1. If `name === undefined || name === null || name === ''`: not a string check, so return `400 { error: 'name is required' }`.
     2. Else if `typeof name !== 'string'`: `400 { error: 'name must be a string' }`.
     3. Else if `!isNonEmptyString(name)` (whitespace only): `400 { error: 'name is required' }`.
   - Simpler equivalent: `if (name == null) required; else if (typeof name !== 'string') must be a string; else if (!isNonEmptyString(name)) required`. Use this form.
   - Call `Users.create({ name: name.trim() })` so only `name` is passed (extra fields are dropped) and the value is trimmed.
   - Respond `201` with the returned user. Errors still go to `next(err)`.
   - No change to `validation.js` (the existing `isNonEmptyString` import is already in `index.js`).

## Risks and notes
- The test mock for `Users.create` spreads its input, so the "extra fields not passed" test must assert on `create`'s call arguments, not only on the response body.
- `Auth.verify` is global middleware and runs before the route, so auth failures take precedence over validation without extra work.
- `spec` criterion 4 includes "no body": supertest with no `.send()` gives `req.body === {}` under `express.json()`, which falls under the `name == null` branch.
- Out of scope, so not touched: `models/users.js`, `schema.sql`, migrations, `GET /users` logic, auth.
