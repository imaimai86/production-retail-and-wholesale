
## Round 1 (2026-10-10)

### Q1: Who merges when the pane form names an existing provider
The brief says the helper's `add` "creates the provider or replaces its fields; `--models` replaces the list", but the pane form, which calls `model add`, must "merge the models; fields left empty keep their value" for an existing provider. It does not say whether the merge happens in the pane or in the helper, whether `--endpoint`, `--key-env` and `--models` are required for an existing provider, or what happens to a stored `effort: true` (the form has no effort field, and `add` without `--effort` would reset it). This decides the `add` contract, its validation tests and the pane test "the form calls `model add` with the four values".
**Suggested:** The pane merges; the helper stays strict. `add` always requires `--endpoint`, `--key-env` and `--models` (a missing one exits 1, nothing written) and replaces every field, including `effort` (false unless `--effort` is given). When the typed provider name already exists in the list the pane has loaded, the pane fills each empty field from the stored provider, sets models to the stored list followed by the typed ones that are not already in it, passes `--effort` when the stored `effort` is true, and then calls `model add` with the four complete values. For a new provider all four fields are required; an empty one shows a toast and nothing is called.
**Answer:** accept

### Q2: Removing the last model of a provider
`remove-model` on a provider with one model would leave an empty list, which the rule "at least one model" forbids. The brief does not say whether the command is rejected or whether it removes the provider too. One loses a provider's endpoint and key variable silently, the other does not.
**Suggested:** Rejected: exit 1, nothing written, stderr says the provider would have no model left and to use `remove <provider>` instead.
**Answer:** accept

### Q3: Commands aimed at something that does not exist, or that already exists
The brief gives `get` on an unknown provider (exit 1) but not: `add-model` or `remove-model` on an unknown provider, `remove-model` of a model the provider does not list, `remove` of an unknown provider, and `add-model` of a model already listed. Each can be an error or a silent success (idempotent); the pane toasts and the tests differ.
**Suggested:** All are errors: exit 1, one stderr line naming the provider or model, nothing written. `add-model` of a model already listed is rejected by the "no duplicate models" rule. `add-model` also applies the model pattern and the 50-model limit.
**Answer:** accept

### Q4: Exact output of `list`, `list --json`, `get` and the writing commands
The brief names the fields but not the shapes. `list --json` is read by the pane and by `add-stage-model-switch`, and `get` is parsed by `sdlc.sh`, so the shapes are contracts: object keyed by provider name or array, how `effort` is written in `get` (`true`/`false` or `yes`/`no`), what `list` prints without `--json`, what is printed when there is no file, and what a successful `add`, `add-model`, `remove-model` or `remove` prints.
**Suggested:** `list --json` prints one line: `{"providers":{"<name>":{"endpoint":"…","api_key_env":"…","models":[…],"effort":false,"key_set":true}}}`, the file's shape plus `key_set`, with `effort` always a boolean; registry providers only (not the `SDLC_PROVIDERS` of `.env`). With no file or no provider: `{"providers":{}}`, exit 0. `list` without `--json` prints one line per provider, `<name>  <endpoint>  <VAR> (key set|key NOT set)  <models comma-joined>`, with `  effort` appended when true, and the single line `no providers (<path>)` when there are none. `get` prints exactly four lines in this order: `endpoint=<url>`, `api_key_env=<VAR>`, `models=<a,b>`, `effort=true|false`. Each writing command prints one line on success, for example `added <provider> (<n> models)`, `added <provider>/<model>`, `removed <provider>/<model>`, `removed <provider>`. A missing file is an empty registry for every reading command (`get` and `test` then exit 1 as unknown provider).
**Answer:** accept

### Q5: Does a hand-edited file that breaks a validation rule count as "wrong shape"
The brief says a file with "the wrong shape" makes every command except `path` exit 1, and lists validation rules for the commands that write. It does not say whether those rules are also checked when the file is read. If they are not, a hand-edited `http://` endpoint on a remote host would be used by `sdlc.sh` and `test`, sending the key in clear text, which the endpoint rule exists to prevent. It also does not say what happens to keys the helper does not know (top level or inside a provider).
**Suggested:** Every rule is checked on read as well. The shape is: a JSON object with a `providers` object; each provider an object with string `endpoint`, string `api_key_env`, array-of-strings `models` and optional boolean `effort`. A file that fails the shape or any validation rule (name, endpoint, `api_key_env`, model pattern, 1 to 50 models, no duplicates) makes every command except `path` exit 1 with the file path and the first offending provider and rule, and `sdlc.sh` exit 1 at startup; the file is left untouched. Unknown keys are tolerated and kept as they are when the file is rewritten.
**Answer:** accept

### Q6: Which `.env` the helper reads, and how
`key_set`, `test` and `sdlc.sh` take the key variable "from the repo-root `.env`" when the shell does not have it. The helper can find that file from the current directory (as `load_env_models` does today with `[ -f .env ]`) or from its own location (`scripts/..`). The tests must point it at a temporary `.env` without touching the real one, and a worktree's `.env` is a symlink. The brief also does not say how the line is parsed or whether an empty value counts as set.
**Suggested:** The `.env` in the current working directory, as `scripts/sdlc.sh` does today; the wrapper and the pane run from the repo root, so it is the repo-root file. Only the line `<VAR>=…` for the one named variable is read (last match wins), with the same handling as `load_env_models`: one pair of surrounding single or double quotes is stripped, no `export` prefix, no interpolation. The shell value wins over `.env`. A variable that is unset or empty in both places is "not set" (`key_set` false; `sdlc.sh` and `test` exit 1 naming the variable).
**Answer:** Why are we using .env? We decided env not the best place for keeping dynamic variables

### Q7: `test` details the brief leaves open
For `test <provider>/<model>` the brief gives the request and the timeout but not: whether a `.env`-only provider (`SDLC_PROVIDERS`) can be tested, what happens when the provider or model is not in the registry or the key variable is not set, which statuses count as success, the `anthropic-version` value, how an endpoint stored with a trailing slash is joined to `/v1/messages`, and what is printed on a timeout or a connection error (there is no HTTP status then).
**Suggested:** Registry providers only. An unknown provider, a model the provider does not list, or an unset key variable exits 1 with a stderr line naming it, and no request is sent. The key comes from the shell, else from `.env` (as in Q6). Trailing slashes of the endpoint are dropped before `/v1/messages` is appended (the endpoint is stored as typed). `anthropic-version: 2023-06-01`. Any 2xx status prints `ok` and exits 0. Any other status prints `HTTP <status>: <first 200 characters of the body>` and exits 1. A timeout prints `timeout after 10s` and a connection error prints `connection failed: <error code>`, both exit 1. The key value appears in no output.
**Answer:** accept

### Q8: How the four-field form behaves in the pane
The plugin's `Input` only reports its text on `Enter` (`onSubmit`), as the answer fields of a paused run do. The brief says `Enter` on the last input calls `model add`, but not what `Enter` does on the first three, how the user sees what was captured, what happens after a successful add, or how the user leaves the Models screen. These are visible behaviours the pane tests must pin down.
**Suggested:** `Enter` on any of the first three inputs saves that field as a draft, shown next to it (as `→ value` on the answer fields today). `Enter` on the fourth saves it and submits with the drafts. On success: a toast with the command's output line, the drafts are cleared and the list is reloaded. On rejection: a toast with the stderr line and the drafts stay. The Models screen has a `← All pipelines` button that returns to the overview, like the other screens. After `Remove` (second press) and after an add, the list is reloaded; a pending `Remove` confirmation has a `Keep it` button, as Discard does.
**Answer:** accept

## Round 2 (2026-10-10)

### Q1: Where the key VALUE of a registry provider is read from
Round 1 Q6 was answered with "Why are we using .env? We decided env not the best place for keeping dynamic variables". The reason it was there: the registry (`models.json`) holds everything dynamic (provider, endpoint, models, the NAME of the key variable), but by decision it never holds the key value, so the value has to come from somewhere else. The brief names two places: the shell environment, "else from that one variable in the repo-root `.env`", and it defines `key_set` as true "when the variable is set in the process environment or in the repo-root `.env`". Your answer reads as rejecting the `.env` half, but it does not say so outright, and dropping it has a visible cost: the variable must then be exported in the shell that starts Claude Code or `sdlc.sh` (for example in `~/.zshrc`), because a key written only in `.env` would no longer be found by the pane, by `test` or by a pipeline. This decides `key_set`, `test`, `resolve_provider`, whether `load_env_models` changes at all, and four of the brief's tests (`key_set` from `.env`, the key "failing that, from `.env`"). Round 1 Q7 was accepted with "the key comes from the shell, else from `.env` (as in Q6)", so it follows whatever is chosen here.
**Suggested:** Shell environment only. For a registry provider the key is the value of the variable named by `api_key_env` in the environment of the process that runs the command (`sdlc-models.cjs`, `sdlc-mod.sh`, `sdlc.sh`); the helper never opens `.env`. `key_set` is true only when that variable is set and not empty in the process environment. A variable that is unset or empty is "not set": `key_set` false, and `test` and `sdlc.sh` exit 1 naming the variable, with no request sent. The brief's tests "`key_set` true from `.env`" and "the key comes from … failing that, from `.env`" are replaced by tests that a value present only in `.env` is NOT used. `README.md` says to export the variable in the shell profile. (Alternative, if you prefer the brief as written: shell first, else the single line `<VAR>=…` of the `.env` in the current directory, with the quote handling of `load_env_models`.)
**Answer:** accept

### Q2: Does the `SDLC_PROVIDER*` block of `.env` stay as a fallback
The same answer could also apply to the existing `.env` providers. Today `scripts/sdlc.sh` reads `SDLC_PROVIDERS` and `SDLC_PROVIDER_<NAME>_ENDPOINT`, `_API_KEY`, `_MODELS`, `_EFFORT` from `.env` (`load_env_models`, `scripts/sdlc.sh:90`), merged in PR #72. The brief keeps that path: `resolve_provider` looks in the registry first, "then falls back to the `SDLC_PROVIDER*` variables", the known providers are "the registry's plus `SDLC_PROVIDERS`", a test requires that "a provider only in `.env` still works", and `.env.example` is to call the block "the fallback for CI and headless runs". If your objection covers this too, that fallback, its test and the `.env.example` block must be removed instead, and anyone using `SDLC_PROVIDER*` today would have to move to the registry. This decides whether `resolve_provider` has one source or two.
**Suggested:** Keep it, exactly as the brief says. The registry is the primary place and wins when a provider is defined in both; `SDLC_PROVIDER*` (from the shell or `.env`, including its own `_API_KEY`) stays untouched as the fallback for CI and headless runs, where there is no pane and no user-level file. This item removes nothing that works today.
**Answer:** accept
