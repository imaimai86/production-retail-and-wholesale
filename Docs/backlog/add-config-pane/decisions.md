
## Round 1 (2026-10-10)

### Q1: How the form collects its four values
The brief says "`Enter` on the last one calls `model add`" and "a rejected add keeps what was typed". In `register.tsx` an `Input` is only ever used with `placeholder` and `onSubmit` (lines 787 and 820): the pane gets a field's text only when Enter is pressed in that field, and nothing in the repo shows that an `Input` can be given a value to display. So it is not defined how the first three values reach the pane when Enter is pressed in the fourth, nor what "keeps what was typed" looks like on screen. This decides the form's state, its key names and most of the form tests.
**Suggested:** Follow the paused-run answers pattern (`draft` atom): Enter in any field stores that field's trimmed text in a `configDraft` atom and the stored value is shown next to the field (`→ <value>`); Enter in the fourth field (models) stores it and then calls `model add` with the four stored values. A field in which Enter was never pressed counts as empty. After a successful add the four stored values are cleared and a toast shows the command's stdout line (`added <provider> (<n> models)`); after a rejected add the stored values stay as they are, which is what "keeps what was typed" means. No `value`/`defaultValue` prop is used on `Input`.
**Answer:** accept

### Q2: Exact merge rule for an existing provider
The brief says "an existing provider name merges the models; empty fields keep the stored value (the screen fills them from the list before calling `add`)". The backend does not merge: `model add` replaces every field of an existing provider (`scripts/sdlc-models.cjs:253`, and `README.md:134` says so), and it rejects a list with a duplicate (`models: duplicate '<m>'`). So the pane has to build the final list itself, and the brief does not say in which order, nor what happens when a typed model is already stored or is typed twice. This decides the `--models` argument the tests assert.
**Suggested:** For a provider name that is in the last `model list --json` result: `--models` is the stored models in their stored order, followed by the typed models that are not already stored, in typed order, each kept once (a typed model that is already stored or repeated is silently dropped, not an error); an empty models field sends the stored list unchanged; an empty endpoint or key-variable field sends the stored value, a non-empty one replaces it. For a provider name that is not in the list, the four typed values are sent exactly as typed (empty ones included) and the backend's own validation message is shown as the error toast; the pane validates nothing itself.
**Answer:** accept

### Q3: The provider's `effort` flag
A registry provider has a fifth field, `effort` (`model add … [--effort]`, returned by `model list --json`). The brief's form has four fields and its screen lists name, endpoint, key variable, key state and models, so `effort` is not mentioned. This matters because `model add` without `--effort` stores `effort: false` (`sdlc-models.cjs:253`, `Boolean(opts.effort)`): adding one model from the pane to a provider that was registered with `--effort` on the command line would silently switch its effort off.
**Suggested:** The pane keeps the stored flag: when the provider already exists and `model list --json` reports `effort: true`, the pane appends `--effort` to the `model add` call; otherwise it does not. A provider created from the pane has no effort (there is no fifth field; `--effort` stays a command-line option). The provider row shows the word `effort` after its models when the flag is true, as the text form of `model list` does, and nothing when it is false.
**Answer:** accept

### Q4: Removing a single model
"Expected behaviour" says the pane "lets the user add, test and remove" providers and models, but the screen decision gives only a per-provider `Remove` and a per-model `Test`. Because the form only merges models (Q2), a single model could never be taken off a provider from the pane: the user would have to remove the whole provider and add it again, or use `model remove-model` on the command line. The backend command exists (`model remove-model <provider> <model>`; it refuses the last model of a provider).
**Suggested:** Add a per-model `Remove` button next to `Test`, with the same second-press confirmation as the provider `Remove`, calling `bash scripts/sdlc-mod.sh model remove-model <provider> <model>`. A refusal (for example the last model: "provider '<p>' would have no model left: use remove <p>") is shown as the error toast like any other non-zero exit. The list refreshes afterwards.
**Answer:** accept

### Q5: What the Test toast shows
The brief says the Test result "(`ok`, or the status and message) is a toast" and, under Errors, "a non-zero exit shows the first stderr line as a toast". `model test` does not fit the second rule: a failed probe exits 1 with its line on **stdout** and an empty stderr (`HTTP 401: …`, `timeout after 10s`, `connection failed: …`, `sdlc-models.cjs:293`), while only the cases where no request is made write to stderr (`key variable <VAR> is not set`, unknown provider or model). With the stderr rule alone a failed probe would give an empty toast. The exact toast text is also asserted by two tests ("`Test` shows an `ok` toast and a failure toast"). A probe can take up to 10 seconds.
**Suggested:** For every pane action the message of a non-zero exit is the first non-empty line of stderr, or, when stderr is empty, the first non-empty line of stdout. The Test toast is `<provider>/<model>: <line>`, where `<line>` is `ok` on exit 0 and that message otherwise (for example `acme/fast: ok`, `acme/fast: HTTP 401: …`, `acme/fast: key variable ACME_KEY is not set`). The `Test` button is shown for every model, also when the provider's key is not set. No progress indicator is shown while the probe runs.
**Answer:** accept

### Q6: Remove confirmation details
The brief says "per provider a `Remove` button (second press confirms, as Stop does)". Stop has three parts the brief does not restate for Remove: its label changes to `Confirm stop`, a separate `Keep running` button cancels it, and the pending confirmation is one slug held in an atom. For Remove it is not stated what the labels are, whether there is a cancel button, whether two providers can be awaiting confirmation at once, and whether a pending confirmation survives closing and reopening the pane. The test "`Remove` needs a second press" asserts these.
**Suggested:** First press changes that provider's button label from `Remove` to `Confirm remove` and shows a `Keep it` button next to it (the label the Discard confirmation uses); `Keep it` cancels. Second press runs `model remove <provider>`, shows the stdout line (`removed <provider>`) as a toast and refreshes the list. Only one confirmation is pending at a time (pressing `Remove` on another row moves it there), and it is cleared whenever the pane is opened. If Q4 is accepted, the per-model `Remove` follows the same rules with its own pending state.
**Answer:** accept
