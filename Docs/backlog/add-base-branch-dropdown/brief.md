# add-base-branch-dropdown

Type: feature
Priority: P2 (normal)
Source: report: "Each task should start from a branch selected in a dropdown, with main selected by default (SDLC control pane: when starting a pipeline, choose the base branch from a dropdown; default main)." Motivating incident: on 2026-10-06 local `main` was found 2 merge commits behind `origin/main`.

## Problem
The SDLC control pane cannot choose the branch a new task starts from. In `scripts/sdlc-mod.sh`, `pick_base()` (lines 63-70) returns `SDLC_BASE` if set, else the first existing of `origin/main`, `main`, `HEAD`. `cmd_run` takes it once (line 105, `base="$(pick_base)"`) and creates the worktree with `git worktree add "$wt" -b "$branch" "$base"` (line 121); an existing branch `sdlc/<slug>` is reused (line 119) and an existing worktree is skipped, so the base is ignored in both cases. The merged-item guard `is_merged()` (line 73, `git log "$2" ... --grep="^test(<slug>): add failing tests"`) and the brief lookup (`git cat-file -e "$base:$docs/brief.md"`, lines 113-114) use the same base, and so do `cmd_discard` (line 192) and `cmd_restart` (lines 211-215). The pane (`.claude/plugins/sdlc-monitor/hooks/register.tsx`) has no way to pass a base: `launch($, slug, from)` (line 238) runs `nohup bash scripts/sdlc-mod.sh run "$0"` detached with env `SDLC_MAX_PARALLEL` (and `FROM`, the resume stage, not a base); `runSelected` (line 272) starts as many selected slugs as free slots (cap 2) and puts the rest in the `queue` atom (line 22, an array of slugs); `drainQueue` (line 287) launches queued slugs when a slot frees; `startRun` (line 253) backs the **Start** button of the page shown after a discard (line 550); pending items render as `[ ]`/`[x]` checkbox Buttons keyed `sel-<slug>` (line 483); the pending list comes from `node scripts/backlog-list.cjs pending --json`, cached 10 s (line 153, `PENDING_EVERY_MS` at line 8). A plain base of `main` would be risky: on 2026-10-06 the local `main` was found 2 merge commits behind `origin/main`, so a task started from it would silently use old code. Verified by reading the code at `origin/main` c3d84bb; nothing was run.

## Expected behaviour
Each pending task row in the pane has a dropdown of branches, `main` selected by default. Starting the task creates its branch and worktree from the chosen base, using the fresher of `origin/<name>` and local `<name>`. The pipeline view shows `from <base>`.

## Decisions
- Wrapper CLI: `run <slug> [--base <name>]` and `restart <slug> [--yes] [--base <name>]` (flags in any order; `restart` currently parses only a positional `--yes`, `scripts/sdlc-mod.sh` line 240, so its parsing changes). `--base` wins over env `SDLC_BASE`, which stays as the fallback; with neither, the default is `main`. `pick_base` becomes the one place that applies this precedence and the resolution rule below, and `cmd_run`, `cmd_discard` and `cmd_restart` keep calling it.
- Validation: `<name>` must match `^[A-Za-z0-9._/-]+$`, not start with `-`, and not contain `..`; a bad value exits 2.
- A name that is neither a local branch nor `origin/<name>` is refused with exit 7 and the message `base branch '<name>' not found (local or origin)`, recorded in the run record through `fail_start` (field `message`, exit_code 7); nothing is created.
- Resolution: `<name>` resolves to `origin/<name>` when that ref exists and the local branch `<name>` (if it exists) is an ancestor of it (local equal or behind); otherwise to the local `<name>`. A local branch ahead of origin is kept. This fixes the stale local `main` case.
- Fetch (decided by the user on 2026-10-06): before creating a NEW branch/worktree the wrapper runs `git fetch --quiet origin <name>` for the chosen name, with a 20 second limit; a failure (offline, no such remote branch, a local-only branch) is only logged in the wrapper log and never stops the start. macOS has no `timeout` command, so the limit needs another mechanism (for example `perl -e 'alarm 20; exec @ARGV'` or a background process that is killed). Resolution (next bullet) runs after the fetch. No fetch happens when an existing branch or worktree is reused.
- The base only applies when a NEW branch/worktree is created. A resumed or existing pipeline keeps its branch; the wrapper logs `base ignored: sdlc/<slug> already exists`, and the pane says so next to the dropdown for items that already have a branch.
- The resolved ref is saved in the run record as `base` and shown in the pipeline view as `from <base>`.
- The merged-item guard and the brief lookup (`cat-file ... "$base:$docs/brief.md"`) use the chosen base.
- Pane dropdown: a `Select` (props `key`, `label`, `options: {value,label}[]`, `value`, `onSelect(value, e)`), default `main`; if no `main` exists, the branch `origin/HEAD` points to, else the first option. Options are all local branches plus remote-only `origin/*` branches (shown without the `origin/` prefix), including the pipeline's own `sdlc/*` branches (so one task can start from another task's branch), excluding only `origin/HEAD`; sorted `main` first, then alphabetical; from one read-only `git for-each-ref` call refreshed with the pending list (every 10 s). Listing needs no network call. (Decided by the user on 2026-10-06.)
- Granularity (decided by the user on 2026-10-06): one dropdown on each pending task row, so every task can start from a different branch. The selection lives in a `bases` atom keyed by slug (default `main`) and is cleared when the task is launched. A queued task keeps the base chosen when it was queued; `drainQueue` passes it (the `queue` atom must carry the base per slug). `launch` passes `--base <name>` to the wrapper.
- Briefs: a brief missing on the chosen base is copied from the main working tree (existing wrapper behaviour, unchanged). A base lacking the item's line in `Docs/backlog/index.md` is allowed; the Ship step's backlog-tick failure in that case is covered by the pending item `fix-ship-commit-scope`.
- Builds on PR #39, which is merged (`c3d84bb`): `pick_base()` / `is_merged()`, `restart`, Discard and the Start page already exist on `origin/main`. The Start page (shown after a discard) gets the same dropdown, and `startRun` passes `--base`. **Resume** does not offer a base (the branch exists, so it would be ignored).

## Scope
- In: `scripts/sdlc-mod.sh`; `.claude/plugins/sdlc-monitor/hooks/register.tsx`, `register.test.ts`, `types/index.d.ts`; `server/__tests__/scripts/sdlc-mod.test.js`; `README.md` (SDLC control section); `CLAUDE.md` (the sdlc-mod command row).
- Out of scope: `scripts/sdlc.sh`; the PR/merge target; creating or deleting branches; choosing a base for Resume; the sdlc-guard plugin.

## Tests
- `server/__tests__/scripts/sdlc-mod.test.js` (throwaway git repos, stub sdlc.sh): `--base <local branch>` starts the worktree from that branch's tip; a remote-only branch works (local bare repo as `origin`); a task can start from another task's `sdlc/<other>` branch; origin fresher than a stale local branch is preferred; a local branch ahead of origin is kept; `--base` beats `SDLC_BASE`; default is main; unknown base exits 7 with the recorded message and creates nothing; invalid names (`--evil`, `a..b`, a name with spaces) exit 2; an existing branch ignores `--base` and logs it; the run record has `base`; the merged guard uses the chosen base; restart accepts `--base`; fetch picks up a new commit pushed to the bare origin before the worktree is created, survives an unreachable origin (start still succeeds, the failure is in the wrapper log), is skipped when the branch or worktree already exists, and does not wait longer than 20 seconds.
- `.claude/plugins/sdlc-monitor/hooks/register.test.ts`: the dropdown lists the stubbed local and remote-only branches, including `sdlc/*` and without `origin/HEAD`, with `main` first and selected by default; choosing another branch changes only that task; Run selected passes `--base <name>` per slug; a queued task keeps its base; the Start page shows the same dropdown and Start passes `--base`; the pipeline view shows `from <base>`; the note appears for an item that already has a branch.
- Not verified at triage: `Select` rendering and keyboard use in a live terminal (the element exists in the terminal table and its props are in the plugin types, but nothing was rendered). Check it by hand during Review.
