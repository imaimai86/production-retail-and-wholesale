# add-base-branch-dropdown

Type: feature
Priority: P2 (normal)
Source: report: "Each task should start from a branch selected in a dropdown, with main selected by default (SDLC control pane: when starting a pipeline, choose the base branch from a dropdown; default main)." Motivating incident: on 2026-10-06 local `main` was found 2 merge commits behind `origin/main`. Extended on 2026-10-06 at the user's request: "modify add-base-branch-dropdown to also allow each pipeline to run in dedicated worktree to keep the local copy intact"; the user chose "Make direct runs always use a worktree" (with an explicit opt-out), then added "the same should apply to sdlc plugin".

## Problem
The SDLC control pane cannot choose the branch a new task starts from. In `scripts/sdlc-mod.sh`, `pick_base()` (lines 63-70) returns `SDLC_BASE` if set, else the first existing of `origin/main`, `main`, `HEAD`. `cmd_run` takes it once (line 105, `base="$(pick_base)"`) and creates the worktree with `git worktree add "$wt" -b "$branch" "$base"` (line 121); an existing branch `sdlc/<slug>` is reused (line 119) and an existing worktree is skipped, so the base is ignored in both cases. The merged-item guard `is_merged()` (line 73, `git log "$2" ... --grep="^test(<slug>): add failing tests"`) and the brief lookup (`git cat-file -e "$base:$docs/brief.md"`, lines 113-114) use the same base, and so do `cmd_discard` (line 192) and `cmd_restart` (lines 211-215). The pane (`.claude/plugins/sdlc-monitor/hooks/register.tsx`) has no way to pass a base: `launch($, slug, from)` (line 238) runs `nohup bash scripts/sdlc-mod.sh run "$0"` detached with env `SDLC_MAX_PARALLEL` (and `FROM`, the resume stage, not a base); `runSelected` (line 272) starts as many selected slugs as free slots (cap 2) and puts the rest in the `queue` atom (line 22, an array of slugs); `drainQueue` (line 287) launches queued slugs when a slot frees; `startRun` (line 253) backs the **Start** button of the page shown after a discard (line 550); pending items render as `[ ]`/`[x]` checkbox Buttons keyed `sel-<slug>` (line 483); the pending list comes from `node scripts/backlog-list.cjs pending --json`, cached 10 s (line 153, `PENDING_EVERY_MS` at line 8). A plain base of `main` would be risky: on 2026-10-06 the local `main` was found 2 merge commits behind `origin/main`, so a task started from it would silently use old code. Verified by reading the code at `origin/main` c3d84bb; nothing was run.

Second part (worktree by default). The pane and `sdlc-mod.sh run` already run every pipeline in its own worktree (`scripts/sdlc-mod.sh:119-121`). A direct `./scripts/sdlc.sh <slug>` (and so `/sdlc`) does not: it runs `git checkout -q -b "$BRANCH"` inside the current checkout (`scripts/sdlc.sh:79`), creates `Docs/backlog/<slug>/logs` there and commits on the branch it switched to, so it disturbs the developer's working copy and current branch. The pane has a matching leftover: runs started by hand are found by their status file in this working tree (`.claude/plugins/sdlc-monitor/hooks/register.tsx:226`) and shown as "Started outside the wrapper ... Resume it in the main working tree with ./scripts/sdlc.sh <slug>" (`:640`). The `sdlc-guard` plugin is loaded into the agents of each worktree run and reads `.claude/sdlc-state.json` relative to the working directory (`.claude/plugins/sdlc-guard/hooks/register.ts:35`): that is right for a worktree, but no test pins it. Verified by reading the code at `origin/main` 4ae14bb; nothing was run.

## Expected behaviour
Each pending task row in the pane has a dropdown of branches, `main` selected by default. Starting the task creates its branch and worktree from the chosen base, using the fresher of `origin/<name>` and local `<name>`. The pipeline view shows `from <base>`.

- `./scripts/sdlc.sh <slug>` (and `/sdlc`) always runs the pipeline in its own dedicated worktree on branch `sdlc/<slug>`; the current checkout, its branch and its uncommitted files are never touched. `--in-place` is the explicit opt-out.
- The control pane and the `sdlc-guard` plugin follow the same rule: nothing is started or resumed in the current checkout, and a run started with `./scripts/sdlc.sh` shows up in the pane like any other run.

## Decisions
- Wrapper CLI: `run <slug> [--base <name>]` and `restart <slug> [--yes] [--base <name>]` (flags in any order; `restart` currently parses only a positional `--yes`, `scripts/sdlc-mod.sh` line 240, so its parsing changes). `--base` wins over env `SDLC_BASE`, which stays as the fallback; with neither, the default is `main`. `pick_base` becomes the one place that applies this precedence and the resolution rule below, and `cmd_run`, `cmd_discard` and `cmd_restart` keep calling it.
- Validation: `<name>` must match `^[A-Za-z0-9._/-]+$`, not start with `-`, and not contain `..`; a bad value exits 2.
- A name that is neither a local branch nor `origin/<name>` is refused with exit 7 and the message `base branch '<name>' not found (local or origin)`, recorded in the run record through `fail_start` (field `message`, exit_code 7); nothing is created.
- Resolution: `<name>` resolves to `origin/<name>` when that ref exists and the local branch `<name>` (if it exists) is an ancestor of it (local equal or behind); otherwise to the local `<name>`. A local branch ahead of origin is kept. This fixes the stale local `main` case.
- Fetch (decided by the user on 2026-10-06): before creating a NEW branch/worktree the wrapper runs `git fetch --quiet origin <name>` for the chosen name, with a 20 second limit; a failure (offline, no such remote branch, a local-only branch) is only logged in the wrapper log and never stops the start. macOS has no `timeout` command, so the limit needs another mechanism (for example `perl -e 'alarm 20; exec @ARGV'` or a background process that is killed). Resolution (next bullet) runs after the fetch. No fetch happens when an existing branch or worktree is reused.
- The base only applies when a NEW branch/worktree is created. A resumed or existing pipeline keeps its branch; the wrapper logs `base ignored: sdlc/<slug> already exists`, and the pane says so next to the dropdown for items that already have a branch.
- The resolved ref is saved in the run record as `base` and shown in the pipeline view as `from <base>`.
- The merged-item guard and the brief lookup (`cat-file ... "$base:$docs/brief.md"`) use the chosen base.
- Pane dropdown: a `Select` (props `key`, `label`, `options: {value,label}[]`, `value`, `onSelect(value, e)`), default `main`; if no `main` exists, the branch `origin/HEAD` points to, else the first option. Options are all local branches plus remote-only `origin/*` branches (shown without the `origin/` prefix), including the pipeline's own `sdlc/*` branches (so one task can start from another task's branch), excluding only `origin/HEAD`; sorted `main` first, then alphabetical; from one read-only `git for-each-ref` call refreshed with the pending list (every 10 s). Listing needs no network call. (Decided by the user on 2026-10-06.)
- Granularity (decided by the user on 2026-10-06): one dropdown on each pending task row, so every task can start from a different branch. The selection lives in a `bases` atom keyed by slug (default `main`) and is cleared when the task is launched. A queued task keeps the base chosen when it was queued; `drainQueue` passes it (the `queue` atom must carry the base per slug). `launch` passes `--base <name>` to the wrapper.
- Briefs: a brief missing on the chosen base is copied from the main working tree (existing wrapper behaviour, unchanged). A base lacking the item's line in `Docs/backlog/index.md` is allowed; the Ship step's backlog-tick failure in that case is covered by the pending item `fix-ship-commit-scope`.
- Builds on PR #39, which is merged (`c3d84bb`): `pick_base()` / `is_merged()`, `restart`, Discard and the Start page already exist on `origin/main`. The Start page (shown after a discard) gets the same dropdown, and `startRun` passes `--base`. **Resume** does not offer a base (the branch exists, so it would be ignored).

- Worktree by default (decided by the user on 2026-10-06: "Make direct runs always use a worktree"; "the same should apply to sdlc plugin").
- Arguments: `./scripts/sdlc.sh [slug] [--in-place] [--base <name>]`, flags in any order; an unknown flag exits 2 with usage. `--base` is passed on to the wrapper (the `--base` of this item); `--base` together with `--in-place` exits 2 with `--base needs a worktree run`.
- Recursion guard: `scripts/sdlc-mod.sh` `cmd_run` exports `SDLC_WRAPPED=1` next to `SDLC_SLUG`, so the copy of `sdlc.sh` that the wrapper starts inside the worktree runs the pipeline and does not delegate again.
- When `SDLC_WRAPPED` is empty and neither `--in-place` nor `SDLC_IN_PLACE=1` is given, `sdlc.sh` resolves the slug (no slug = first `- [ ]` item of the primary checkout's `Docs/backlog/index.md`, as today), checks that the brief exists as today, validates `FROM` as today (the cheap checks stay first, so they still fail with no side effects), and then `exec`s the delegation below. The delegation happens BEFORE `mkdir -p "$LOG"`, before any git write and before the `git checkout`, so the primary checkout is not changed at all (no branch switch, no `logs/` folder).
- Delegation: print `Running in worktree <path> on branch sdlc/<slug>`, then the monitor command with that path (`watch -n3 'cat <path>/Docs/backlog/<slug>/logs/status.json; git -C <path> status --short | head -15'`) and the output file `<path>/Docs/backlog/<slug>/logs/run.out`. Then run `bash scripts/sdlc-mod.sh run <slug> [--base <name>]` in the foreground (`FROM` and the other environment variables pass through) while following the worktree's `run.out` on the terminal (`tail -F` started before it and stopped when the wrapper exits). Exit with the wrapper's exit code: 0 done, 1 a gate failed, 2 paused for questions, 3 too many runs, 4 already running, 5 already merged, 7 base not found; for a code other than 0, 1 or 2 also print the `message` from the wrapper's run record. On exit 2 also print `Questions are in <path>/Docs/backlog/<slug>/questions.md. Answer them there, then run ./scripts/sdlc.sh <slug> again.`
- Resume: running `./scripts/sdlc.sh <slug>` again reuses the existing worktree and branch (the wrapper already does this), and `FROM=...` resume points pass through.
- New wrapper command `scripts/sdlc-mod.sh where <slug>`: prints the worktree path (`${SDLC_WT_BASE:-<repo parent>/<repo>-sdlc}/<slug>`), has no side effects, and exits 0 even when the worktree does not exist yet. `sdlc.sh`, the docs and `CLAUDE.md` use it, so only one place knows the path.
- `--in-place` (or `SDLC_IN_PLACE=1`) keeps today's behaviour exactly (branch switch in the current checkout) and first prints `WARNING: running in place: this checkout will be switched to sdlc/<slug>`.
- `.claude/commands/sdlc.md` and the monitor-command rule in `CLAUDE.md` use the worktree path (`$(bash scripts/sdlc-mod.sh where <slug>)`) in the `watch` command and say that `questions.md` and `decisions.md` are in the worktree. The single-stage commands (`/spec`, `/plan`, `/red-tests`, `/implement`, `/review`, `/ship`) are unchanged.
- sdlc-monitor pane: it starts and resumes runs only through `scripts/sdlc-mod.sh run`, as today; no code path may call `scripts/sdlc.sh` or pass `--in-place`. A run started with `./scripts/sdlc.sh` now has a wrapper run record, so it is listed with Stop and Resume like any other. The "started outside the wrapper" branch (`register.tsx:226` and `:640`) stays only for `--in-place` runs found by their status file in this working tree, and its note becomes `Started with --in-place, so it runs in this checkout: Stop and Resume are not available here. Use ./scripts/sdlc.sh <slug> (worktree, the default) to keep this checkout untouched.` The pipeline view shows the worktree path next to `from <base>`.
- sdlc-guard plugin: no behaviour change. It keeps loading from the primary checkout's plugin folder (`CLAUDE_CODE_PLUGIN_DIRS`) and reads `.claude/sdlc-state.json` and other files relative to the agent's working directory, which is the worktree; tests pin that it never reads or writes the primary checkout.
- Unchanged: the wrapper already links `.env`, `node_modules` and `graft` from the primary checkout into each worktree.

## Scope
- In: `scripts/sdlc-mod.sh`; `.claude/plugins/sdlc-monitor/hooks/register.tsx`, `register.test.ts`, `types/index.d.ts`; `server/__tests__/scripts/sdlc-mod.test.js`; `README.md` (SDLC control section); `CLAUDE.md` (the sdlc-mod command row).
- Out of scope: `scripts/sdlc.sh`; the PR/merge target; creating or deleting branches; choosing a base for Resume; the sdlc-guard plugin.

- Also in scope for the worktree part: `scripts/sdlc.sh` (argument parsing and delegation only; the pipeline stages are not touched), `.claude/commands/sdlc.md`, and tests only in `.claude/plugins/sdlc-guard/hooks/register.test.ts`.
- Also out of scope: the single-stage commands, the semantics of `discard` and `restart`, where worktrees live, `.claude/plugins/*/tsconfig.json`.
- Ordering: this item now also edits `scripts/sdlc.sh`, so run it after `fix-ship-commit-scope`, `add-test-repair-resume` and `retry-unclaimed-failing-test` have merged. Tests in those items that execute `sdlc.sh` directly (for example the `FROM=bogus` test) must then pass `SDLC_WRAPPED=1` or `--in-place`.

## Tests
- `server/__tests__/scripts/sdlc-mod.test.js` (throwaway git repos, stub sdlc.sh): `--base <local branch>` starts the worktree from that branch's tip; a remote-only branch works (local bare repo as `origin`); a task can start from another task's `sdlc/<other>` branch; origin fresher than a stale local branch is preferred; a local branch ahead of origin is kept; `--base` beats `SDLC_BASE`; default is main; unknown base exits 7 with the recorded message and creates nothing; invalid names (`--evil`, `a..b`, a name with spaces) exit 2; an existing branch ignores `--base` and logs it; the run record has `base`; the merged guard uses the chosen base; restart accepts `--base`; fetch picks up a new commit pushed to the bare origin before the worktree is created, survives an unreachable origin (start still succeeds, the failure is in the wrapper log), is skipped when the branch or worktree already exists, and does not wait longer than 20 seconds.
- `.claude/plugins/sdlc-monitor/hooks/register.test.ts`: the dropdown lists the stubbed local and remote-only branches, including `sdlc/*` and without `origin/HEAD`, with `main` first and selected by default; choosing another branch changes only that task; Run selected passes `--base <name>` per slug; a queued task keeps its base; the Start page shows the same dropdown and Start passes `--base`; the pipeline view shows `from <base>`; the note appears for an item that already has a branch.
- Not verified at triage: `Select` rendering and keyboard use in a live terminal (the element exists in the terminal table and its props are in the plugin types, but nothing was rendered). Check it by hand during Review.

- New `server/__tests__/scripts/sdlc-worktree-default.test.js` (throwaway git repos; a stub `scripts/sdlc-mod.sh` that records its arguments and environment and exits with a chosen code): plain `sdlc.sh <slug>` calls the wrapper with `run <slug>` and creates no branch, no `logs/` folder and no file in the primary checkout (`git status`, `git branch` and the file list are unchanged); `--base <name>` is forwarded; `--base` with `--in-place` exits 2; with `SDLC_WRAPPED=1` it does not delegate; `--in-place` and `SDLC_IN_PLACE=1` print the WARNING and do not delegate; no slug picks the first `- [ ]` item; an unknown flag exits 2; `FROM=bogus` still exits 1 before delegating; the wrapper's exit codes 0, 1, 2, 3, 4, 5 and 7 come back unchanged; for exit 2 the questions message with the worktree path is printed; the header shows the worktree path and a `watch` command containing it; `where <slug>` prints the path and has no side effects; and in `sdlc-mod.test.js`, `cmd_run` exports `SDLC_WRAPPED=1` to the process it starts (assert with the stub `sdlc.sh`).
- `.claude/plugins/sdlc-monitor/hooks/register.test.ts`: no command the pane runs contains `scripts/sdlc.sh` or `--in-place`; a slug that has a wrapper record (started by `./scripts/sdlc.sh`) shows Stop and Resume; an in-place run found by its status file shows the new note and no Stop or Resume; the view shows the worktree path.
- `.claude/plugins/sdlc-guard/hooks/register.test.ts`: with the working directory set to a worktree folder, the guard reads `.claude/sdlc-state.json` from that folder, and nothing under the primary checkout's path is read or written.
