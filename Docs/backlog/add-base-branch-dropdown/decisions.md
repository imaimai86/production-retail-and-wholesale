
## Round 1 (2026-10-07)

### Q1: When is an unknown base refused if the branch or worktree already exists?
The brief says an unknown `<name>` exits 7 and "nothing is created", and that an existing branch/worktree ignores `--base` with the log line `base ignored: sdlc/<slug> already exists`. It does not say what happens on a resume or a re-run when the item already has its branch/worktree and `--base` (or `SDLC_BASE`) names a branch that does not exist. Today `cmd_run` calls `pick_base` before the existence check, so the order decides whether a resume of an old pipeline can suddenly fail with exit 7 (for example after the base branch was deleted). The same question applies to `discard` and `restart`, which call `pick_base` only for the "commits not in base" count and the merged guard.
**Suggested:** Name validation (exit 2) always applies. The existence check (exit 7) applies only when a NEW branch/worktree would be created. When the branch or worktree exists, the base is ignored (logged as in the brief) and an unknown base does not fail the run; the run record `base` is then left empty/unchanged. For `discard`, and for `restart`'s merged guard, an unresolvable base skips the "not in base" count and the guard instead of failing (with a note in the output).
**Answer:** Always block with a warning: an unknown base ALWAYS fails with exit 7 and a clear warning that names the unknown base, including on a resume, discard or restart when the item's branch or worktree already exists. (This replaces the suggested 'ignore the base when the branch exists'.)

### Q2: What happens when no base is given and `main` does not exist?
The brief says "with neither (`--base` nor `SDLC_BASE`), the default is `main`" and that a name that is neither a local branch nor `origin/<name>` exits 7. Today `pick_base` falls back from `origin/main` to `main` to `HEAD`, so a repository whose default branch has another name (or a throwaway test repo with no `main`) still starts. Removing the `HEAD` fallback changes that. The pane already falls back to the branch `origin/HEAD` points to, then the first option, but the wrapper CLI has no such rule.
**Suggested:** The wrapper applies the same fallback as the pane when the default is used: `main`, else the branch `origin/HEAD` points to, else the current `HEAD` (as today). This fallback applies only when neither `--base` nor `SDLC_BASE` is given; an explicitly named base that is missing always exits 7.
**Answer:** Find the default branch if possible: when neither --base nor SDLC_BASE is given, use main; if main does not exist, use the branch origin/HEAD points to; if neither can be found, use the current HEAD as today. An explicitly named base that is missing always exits 7.

## Round 2 (2026-10-08)

### Q1: What does the run record `base` and the pipeline view's `from <base>` show when the base is ignored?
The brief says the resolved ref is saved in the run record as `base` and shown as `from <base>`, and that on a resume or re-run with an existing branch/worktree the base is ignored (logged as `base ignored: sdlc/<slug> already exists`). Round 1 Q1 now makes an unknown base fail with exit 7 even then, so the base is still resolved on a resume. It is not stated what gets recorded in that case: the freshly resolved (but unused) base, nothing, or the base the branch was originally created from. Recording the unused base would make the pipeline view claim `from <base>` for a branch that was never created from it.
**Suggested:** On a resume/re-run with an existing branch or worktree, the run record keeps the `base` value stored when the branch was created (empty if none was stored) and is never overwritten by the ignored base. A `base` is written only when a NEW branch/worktree is created. The pipeline view shows `from <base>` only when the record has a base, and shows nothing otherwise.
**Answer:** Overwrite with the resolved base: the run record's `base` is written with the freshly resolved base on EVERY run, including a resume or re-run where the existing branch/worktree makes the base ignored. The pipeline view shows `from <base>` from that record value. (This replaces the suggested 'keep the base stored at creation'. The user chose it knowing the pane could then show a base the branch was not created from.)
